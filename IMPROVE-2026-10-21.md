# Improvement Deep-Dive — nosflare — 2026-10-21

Scope: main (v7.9.45), v8-staging branch, patches/. Sources read: `src/relay-worker.ts`, `src/durable-object.ts`, `src/config.ts` (main + v8-staging), `wrangler.toml`, `package.json`, v8 commit log.

## Top recommendations (ranked, with effort S/M/L)

1. **v8-staging is a config shell, not a relay (L).** `src/relay-worker.ts` on v8-staging is byte-identical to main v7.9.45. `src/config.ts` on v8-staging references `ConnectionDO`, `SessionManagerDO`, `EventShardDO`, `PaymentDO` (sharding flags, `PAYMENT_DO_SHARDING_ENABLED`, etc.) and patch `0003-owner-paywall-exemption.patch` patches `src/connection-do.ts` — none of those files exist in the branch. The branch cannot build the architecture it describes. Either commit the real sharded-DO v8 code or re-scope the branch to "v7.9.45 + 0xServerless config" so nobody deploys a config that lies about its runtime.
2. **Fix the unverified `notify-zap` admission path before v8 ships any paywall (M).** `handlePaymentNotification` (relay-worker.ts ~L2180) accepts `POST /?notify-zap&npub=<hex>` and calls `savePaidPubkey` — no zap-receipt validation, no signature check, no amount check. Anyone can self-grant paid access. The v8 fix (the SIP-Booster pattern) should: require a kind-9735 zap receipt in the POST body; verify its Schnorr signature; require the receipt's `bolt11` tag and validate the invoice amount >= `RELAY_ACCESS_PRICE_SATS`; require `p` tag == payer pubkey and `P` tag == relay pubkey; persist the receipt event id (D1 uniqueness) for replay protection; only then mark paid. Keep the endpoint behind a shared-secret or the LNURL callback URL being unguessable as defense-in-depth.
3. **NIP-42 re-enable decision: keep it ON for the paid relay (S).** v7's DO implements NIP-42 correctly (challenge, kind 22242, relay-host check, hibernation persistence via `serializeAttachment`). v8-staging config sets `limitation.auth_required: false` (driving `AUTH_REQUIRED=false`) while `PAY_TO_RELAY_ENABLED=true` — leaving the bypassable paywall as the only gate and weakening per-pubkey rate accounting. Recommendation: `auth_required: true` on the paid profile; only disable auth on a free/read-mostly profile. Also fix `supported_nips` honesty (below).
4. **Dependency lift (S):** wrangler ^3.0.0 → **^4.149.0** (v3 bug-fix support ended Q1 2026, critical security only until Q1 2027; CVE-2026-0933 command injection affects wrangler <3.114.17 and 4.0–4.59.0 — the ^3 range can resolve to vulnerable versions). esbuild ^0.19.12 → **0.28.2**. `@cloudflare/workers-types` ^4 dated → **v5** (Jul 2026: dated entrypoints removed; or switch to `wrangler types` codegen). See below for @noble/curves.

## Missing gates (CI/tests/protection)

- **No `.github/` at all**: no CI, no tests, no lint. A broken `main` would deploy silently. Minimum gate: GitHub Actions workflow running `npm run typecheck` + `npm run build` on push/PR.
- **Committed build artifacts drift**: `worker.js` (214 KB), `nostr-zap.js` (209 KB), `send-it.js` (83 KB) are checked in with no rebuild check. CI should rebuild and `git diff --exit-code worker.js` so the shipped bundle provably matches `src/`.
- **No secret scanning**: add gitleaks (the repo carries npubs/D1 IDs; a future committed API key would be caught).
- **No branch protection on main** (audit branches show unprotected); protect main + require the CI gate.

## Quick wins (code/config)

- **`handleReq` forces `filter.limit = 500`** even when the client asks for less-is-more paging; combined with the 60 s local query cache + 300 s `caches.default` global cache, clients doing sync-style sequential REQ paging can be served stale pages. For a sync-friendly posture: key the global cache on `(filters, bookmark)` (already done) but skip caching entirely when `limit` is absent/large or when the filter is time-open-ended (`since` only), and honor client `limit` exactly.
- **EOSE completeness hint (NIP-67-style)**: emit `['EOSE', subId, <hint>]`-style completeness signaling (or at minimum a NOTICE when results were truncated at the limit) so sync clients know whether to page or re-REQ. This is the cheap 80% of "NIP-67 for sync" without a protocol change.
- **NIP-66 blasting for send-it.js**: the blaster should source its target list from kind-30166 discovery events on meta-relays (relay.nostr.watch, relaypag.es, monitorlizard.nostr1.com) instead of a static list; filter by monitored-online status and RTT. Turns the blaster into a self-updating tool.
- **Rate-limit `?notify-zap` and `/api/check-payment`** endpoints; today they're unthrottled.
- **`getOptimalDO` hardcoded 9-endpoint list is duplicated** in `relay-worker.ts` and `durable-object.ts` (`ALLOWED_ENDPOINTS`/`ENDPOINT_HINTS`) — extract to a shared module; they already disagree on redirect comments (SAM→enam etc.).
- `wrangler.toml` comment "lower to 10 if not on paid plan" for `cpu_ms` is misleading (10 ms free CPU is per-request, not a safe default for a WS relay); document free-plan infeasibility instead.

## Ecosystem alignment notes

- **Workers limits (verified Oct 2026)**: 128 MB memory per isolate (DOs included) — more headroom than the assumed 64 MiB; SQLite-backed DO storage 10 GB/object; DO soft limit ~1000 req/s per object; inbound WS message cap 32 MiB; cpu_ms 300000 is already the max. The current design (hibernation, 100-entry query cache, persisted subscriptions) fits comfortably; the real ceiling is D1's 10 GB (pruning at 9 GB configured — good).
- **Connection limit relaxed (Apr 2026)**: the 6-simultaneous-connections rule now only counts connections waiting for response headers. The DO-to-DO broadcast fan-out (8 parallel stub.fetch with 3 s timeout) is fine; no change needed.
- **NIP-11 honesty**: v8-staging advertises `supported_nips: [1,2,4,5,9,11,12,15,16,17,20,22,23,33,40,42,50,51,58,65,71,78,89,94]` over byte-identical v7 code. There is no NIP-50 `search` handling in `queryEvents`, no NIP-65-specific logic, no NIP-42 when `auth_required:false`. Trim the list to what the code implements (main's list is mostly accurate) or implement before advertising — NIP-66 monitors and clients (e.g. the 0xRelayFinder auto-tagger) take this list at face value.
- **NIP-01 empty-filter / EOSE semantics**: `handleReq` correctly sends EOSE after stored results; keep the live-stream-after-EOSE behavior (already present via subscriptions) and add the completeness hint above.
- Consider **NIP-86 (management API)** and a **NIP-66 self-check** (publish the relay's own 30166 via an operator monitor) so the relay shows up in 2026-era discovery.
