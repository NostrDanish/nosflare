# Security Audit — nosflare — 2026-10-20

## Summary

Fork of Spl0itable/nosflare (serverless Nostr relay: Cloudflare Worker + Durable Objects + D1). `main` is byte-identical to upstream v7.9.45 (HEAD 1f92b1a, 2026-06-18 — the latest upstream release; nothing to catch up on). A `v8-staging` branch contains the fork owner's work: rebranded config (relay "0xServerless", version labeled 8.9.26), an owner paywall-exemption patch, and build notes — but the `src/` there is still the v7.9.45 codebase (the actual v8 build it references is not in this repo). The most serious issue is inherited from upstream and present on `main`: an **unauthenticated HTTP endpoint that marks any pubkey as paid**, fully bypassing the pay-to-relay gate. NIP-42 auth, event signature verification, allowlist helpers, and rate limiting are otherwise implemented correctly.

Findings: 1 Critical / 1 High / 4 Medium / 2 Low

## Findings

| ID | Severity | File/Area | Issue | Recommended fix |
|----|----------|-----------|-------|-----------------|
| NOS-01 | CRITICAL | `src/relay-worker.ts` `handlePaymentNotification()` + fetch router (`POST /?notify-zap&npub=…`) | Unauthenticated, unvalidated payment-notification endpoint: any internet caller can `POST` with an arbitrary `npub`/pubkey parameter and `savePaidPubkey()` writes it into `paid_pubkeys` — no NIP-57 zap-receipt verification, no shared secret, no signature. This silently grants free write access on a pay-to-relay deployment (`PAY_TO_RELAY_ENABLED = true` in both `main` and `v8-staging` configs). Payment gate = broken. | Require a signed NIP-57 zap receipt (kind 9735) validated against the relay npub and amount, or at minimum a shared-secret/authenticated webhook; until fixed, set `PAY_TO_RELAY_ENABLED = false` or treat the paywall as decorative. Inherited from upstream — also report upstream. |
| NOS-02 | HIGH | `src/config.ts` @ `v8-staging` | v8-staging config sets `limitation.auth_required: false` (NIP-42 disabled) while keeping `payment_required: true`. Combined with NOS-01, the relay is fully open: no auth, fakeable payment. Rate limits were also loosened ~60x (600 EVENT/min, 300 REQ/min vs upstream 10/50 per session). | Enable NIP-42 (`auth_required: true`) on paid relays; keep conservative rate limits unless capacity-tested. |
| NOS-03 | MEDIUM | `src/config.ts` @ `v8-staging` + `patches/0003-owner-paywall-exemption.patch` | Version string claims 8.9.26 and config exposes v8 sharding flags (`CONNECTION_DO_SHARDING_ENABLED`, `SESSION_MANAGER_SHARD_COUNT`, `PAYMENT_DO_SHARDING_ENABLED`, …) but `src/` is still v7.9.45 code — the flags are dead config and the owner-exemption patch targets `src/connection-do.ts`, **a file that does not exist in this repo**. Risk of deploying a mislabeled build whose actual behavior differs from operator expectations. | Commit the real v8 source or correct the version/labels; apply the owner-exemption to the code that actually runs (`durable-object.ts` paywall check on v7). |
| NOS-04 | MEDIUM | `src/relay-worker.ts` `serveLandingPage()` | Landing page hot-loads third-party JS: `cdn.jsdelivr.net/gh/Spl0itable/nosflare@main/nostr-zap.js` and `unpkg.com/nostr-login@latest`. The upstream author (or a compromised CDN package) can change what executes on your relay's payment page — supply-chain risk on a page that asks users to pay. Also on `main`, `relayNpub`/relay identity still point to the upstream author (Luxas/Spl0itable): if deployed unmodified, payments would go to upstream's npub. | Vendor/pin the scripts (SRI hashes), and set your own `relayNpub`, `nip05Users`, contact before deploying. |
| NOS-05 | MEDIUM | `src/durable-object.ts` `handleEvent()` | Kind 1059 (gift wrap) bypasses pubkey allowlist, blocklist and payment checks by design. If the operator ever uses `allowedPubkeys` to run an invite-only relay, kind-1059 writes remain open to anyone authenticated. | Document the carve-out; optionally require payment/allowlist match on the gift-wrap's recipient p-tag instead. |
| NOS-06 | MEDIUM | `src/durable-object.ts` | Rate limiters are per-WebSocket-session token buckets; reconnecting resets them. Query DoS mitigations exist (complexity cap, COUNT precheck, 500 global max) — good — but EVENT spam via reconnect churn is cheap. | Add per-pubkey (post-auth) limiting in DO storage, not only per-connection. |
| NOS-07 | LOW | `wrangler.toml` | Real D1 `database_id` committed (not a secret, but leaks infrastructure identity; fork operators routinely forget to change it, which can point a deploy at the wrong DB). | Move to a template value + docs; rotate if the DB matters. |
| NOS-08 | LOW | Repo hygiene | No SECURITY.md; `main` and `v7-*` branches all carry upstream's identity in config (contact email, npub, icon URL). | Add SECURITY.md; strip/rebrand upstream identity on the fork's main. |

## Secrets Check

- Reviewed: `wrangler.toml`, `package.json`, `src/config.ts` (both branches), `src/relay-worker.ts`, `src/durable-object.ts`, both patch files.
- GitHub secret scanning unavailable (no Advanced Security); code search indexing incomplete — files were read in full instead.
- **No private keys, API tokens, or committed secrets found.** Committed values are public npubs/pubkeys and a D1 database UUID (see NOS-07). `relayNpub` values are public keys — not secrets.

## Dependency Notes

- Minimal and good: only `@noble/curves ^1.6.0` at runtime; dev: esbuild, wrangler ^3 (major versions behind current wrangler 4.x — dev-only, low risk).
- `worker.js` (214 KB) and `nostr-zap.js`/`send-it.js` are committed build artifacts — ensure `worker.js` is rebuilt from audited `src/` before deploy; committed artifacts can silently drift from source.

## Fork/Upstream Freshness

- Fork `main` HEAD = upstream `Spl0itable/nosflare` HEAD = 1f92b1a (v7.9.45, 2026-06-18). **0 commits behind; upstream has no newer release** (latest release v7.9.45). No missing upstream fixes.
- `v8-staging` (last commit 2026-09-29) is fork-only work on top of v7.9.45; see NOS-03.

## Recommended Actions

1. [CRITICAL] Fix or disable the `notify-zap` payment-notification endpoint (require verified NIP-57 zap receipts); report upstream (NOS-01).
2. [HIGH] On v8-staging: enable NIP-42 auth, restore sane rate limits (NOS-02).
3. [MEDIUM] Commit the real v8 source or fix the version label; make the owner paywall exemption target real code (NOS-03).
4. [MEDIUM] Vendor/pin landing-page scripts; rebrand config identity before any deployment (NOS-04).
5. [MEDIUM] Decide and document the kind-1059 allowlist/paywall carve-out (NOS-05).
6. [LOW] Template the D1 database_id; add SECURITY.md (NOS-07, NOS-08).
